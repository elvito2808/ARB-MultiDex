# برنامه تحویل MVP قابل اجرا در ۲۴ ساعت — ARB-MultiDex

**تصمیم مالک:** زبان Python  
**مبنای حاکمیت:** شاخه `agent-governance`  
**بازار مرجع DEX:** Hedera Mainnet / SaucerSwap V1 / WHBAR-USDC  
**حالت تحویل:** SIMULATION / DRY-RUN  
**هدف:** یک اجرای سرتاسری قابل تکرار از دریافت داده تا تشخیص فرصت و اجرای فرضی، همراه با تست و گزارش.

## 1. معنی «قابل اجرا» در این تحویل

MVP باید با دستور روشن از ریشه مخزن اجرا شود، تنظیمات نمونه داشته باشد، وابستگی‌ها مستند باشند، بدون نیاز به کلید خصوصی یا موجودی واقعی کار کند و در حالت SIMULATION/DRY-RUN خروجی قابل مشاهده تولید کند.

در صورت دسترسی پایدار به منابع عمومی، قیمت بازار DEX و KuCoin به‌صورت فقط‌خواندنی دریافت می‌شود. اگر اتصال عمومی در محیط تست در دسترس نباشد، منبع ساختگی باید به‌عنوان fallback صریح وجود داشته باشد. هیچ داده ساختگی نباید به‌عنوان داده زنده معرفی شود.

**این تحویل شامل LIVE trading نیست:** هیچ سفارش واقعی KuCoin، تراکنش زنجیره، امضا، Approval، انتقال دارایی یا استفاده از کلید خصوصی مجاز نیست. فعال‌سازی LIVE نیازمند تصمیم و بازبینی جداگانه مالک است.

## 2. قواعد غیرقابل مذاکره

- زبان Python؛ انتخاب مجدد زبان ممنوع.
- حداکثر سه رابطه/Worker مستقل مطابق اسناد.
- جفت‌ها و استخرها فقط از پیکربندی صریح کاربر؛ انتخاب خودکار استخر ممنوع.
- مقدار پایه هر رابطه قابل تنظیم و مستقل باشد.
- محاسبات مالی فقط با integer/Decimal دقیق؛ float برای محاسبات مالی ممنوع.
- Quote فقط مطابق `docs/design/quote-contract.md` تولید و مصرف شود. قرارداد فعلی فقط تولیدکننده SIMULATION را در مسیر کامل می‌پذیرد؛ آن را بی‌صدا به LIVE گسترش ندهید.
- DEX و KuCoin داده بازار را فقط‌خواندنی دریافت می‌کنند.
- اجرای سفارش و تراکنش صرفاً شبیه‌سازی شود.
- هیچ Secret، private key، seed phrase یا API secret در مخزن، لاگ یا خروجی ثبت نشود.
- هیچ ایجنتی فایل مشترک خارج از مسیرهای تخصیص‌یافته را تغییر ندهد.
- تست‌های آفلاین باید بدون اینترنت و بدون حساب خارجی قابل اجرا باشند.

## 3. مالکیت و مسیرهای مجاز

| ایجنت | مالکیت | مسیرهای مجاز پیشنهادی |
|---|---|---|
| S1 | Connections، DEX، KuCoin market data و Quote producer | `src/arb_multidex/connections/**`, `src/arb_multidex/dex/**`, `src/arb_multidex/kucoin/**`, `src/arb_multidex/quotes/**`, `config/markets.example.yaml` |
| S2 | Quote consumer، مقایسه دو جهت و Opportunity detection | `src/arb_multidex/opportunity/**` |
| S3 | اجرای شبیه‌سازی‌شده، موجودی فرضی، رزرو و Recovery | `src/arb_multidex/execution/**` |
| S4 | Lifecycle، Worker control، Logging، CLI و orchestration | `src/arb_multidex/lifecycle/**`, `src/arb_multidex/observability/**`, `src/arb_multidex/app.py`, `src/arb_multidex/cli.py` |
| S5 | آزمون، بازبینی امنیتی و پوشش تست | `tests/**`, `docs/reviews/**` |

Agent 0 مالک یکپارچه‌سازی، رفع تعارض، قراردادهای مشترک و پذیرش است. اگر ساختار موجود متفاوت است، ایجنت پیش از تغییر مسیر باید ساختار را گزارش و در محدوده وظیفه خودش با کمترین تغییر سازگار شود؛ فایل‌های مالک دیگر را تغییر ندهد.

## 4. ترتیب اجرا

### مرحله A — پایه مشترک و قراردادها
S1 قرارداد داده بازار و Quote producer را مطابق SIM-01 پیاده‌سازی می‌کند. S2 مصرف‌کننده را مطابق همان قرارداد می‌سازد. هر اختلاف نیازمند گزارش به Agent 0 است، نه تغییر خودسرانه قرارداد.

### مرحله B — مسیر سرتاسری
S3 اجرای فرضی و به‌روزرسانی موجودی شبیه‌سازی‌شده را فراهم می‌کند. S4 چرخه عمر، اجرای CLI، لاگ و اتصال اجزا را تکمیل می‌کند.

### مرحله C — اعتبارسنجی
S5 تست‌های آفلاین، منفی، مرزهای امنیتی و تست سرتاسری را اجرا می‌کند. Agent 0 نتایج را بررسی و یکپارچه می‌کند.

## 5. حداقل قابلیت‌های لازم

1. بارگذاری و اعتبارسنجی تنظیمات بازار و حالت اجرا.
2. اتصال فقط‌خواندنی به Hedera RPC و بررسی Chain ID برابر 295.
3. خواندن Pair/Token/Reserve برای استخر انتخاب‌شده و محاسبه BUY/SELL با حجم پایه قابل تنظیم.
4. دریافت یا شبیه‌سازی داده بازار KuCoin؛ نگاشت HBAR-USDT فقط در صورت وجود تنظیم صریح بازار.
5. Quoteهای معتبر و هم‌بسته با شناسه درخواست، زمان مشاهده، نسل اتصال و هزینه‌ها.
6. بررسی هر دو جهت آربیتراژ و اعمال آستانه قابل تنظیم.
7. اجرای فرضی دو سمت با ترتیب و سیاست‌های ثبت‌شده؛ بدون ارسال سفارش یا تراکنش واقعی.
8. موجودی فرضی، رزرو و آزادسازی، ثبت نتیجه و رویداد INCOMPLETE_ARBITRAGE در شبیه‌سازی.
9. Worker مستقل، Start/Stop کنترل‌شده، توقف در خطای متوالی و لاگ مرکزی.
10. دستور اجرای CLI و تست‌های آفلاین با خروجی روشن.

اگر بخشی از اتصال زنده در ۲۴ ساعت به دلیل endpoint، rate limit یا نبود تنظیم کاربر تکمیل نشد، MVP باید با adapter ساختگی اجرا شود و محدودیت به‌صراحت گزارش شود؛ ادعای اتصال زنده ممنوع است.

## 6. معیار پذیرش Agent 0

- نصب وابستگی‌ها از فایل dependency pin شده و اجرای دستور مستند موفق باشد.
- تست‌های آفلاین در محیط پاک موفق باشند.
- اجرای نمونه SIMULATION بدون Secret و بدون اینترنت ممکن باشد.
- در صورت فعال‌بودن adapter عمومی، منبع داده و زمان مشاهده قابل تشخیص باشد.
- خروجی Quote با SIM-01 منطبق باشد؛ هزینه‌ها دوباره کسر نشوند.
- هر دو جهت فرصت به‌درستی محاسبه شوند.
- عملیات شبیه‌سازی‌شده به‌عنوان LIVE ثبت نشود.
- هیچ تراکنش، امضا، Approval یا سفارش واقعی ارسال نشود.
- خطا، قطع داده و stale quote مانع انتشار فرصت شوند.
- راهنمای اجرای سریع و فایل تنظیمات نمونه وجود داشته باشد.
- S2 و S5 بازبینی مستقل خود را با شواهد ثبت کنند.
- Agent 0 SHA نهایی و فایل‌های پذیرفته‌شده را ثبت کند.

## 7. قالب گزارش هر ایجنت

- Task ID و Revision
- Base branch و Base SHA
- Branch و commit SHA خروجی
- فایل‌های ایجاد/تغییرکرده
- دستورهای اجراشده
- تست‌ها و نتیجه دقیق
- مواردی که اجرا نشده‌اند و علت
- وابستگی/مانع واقعی
- تطبیق معیارهای پذیرش: PASS/FAIL
- تأیید اینکه خارج از دامنه تغییری انجام نشده است

## 8. خارج از دامنه این مهلت

- فعال‌سازی LIVE
- نگهداری یا دریافت کلید خصوصی
- ارسال تراکنش یا سفارش واقعی
- Approval واقعی و انتقال دارایی
- انتخاب خودکار DEX، شبکه، استخر یا جفت‌ارز
- ادعای production-ready بودن
- ساخت زیرساخت Microservices یا ابزارهای پیچیده غیرضروری

**اصل مدیریت زمان:** اگر محدودیت زمانی وجود داشت، ابتدا یک مسیر کامل و قابل اجرا با تست آفلاین تحویل شود؛ سپس اتصال‌های زنده و قابلیت‌های توسعه‌ای افزوده شوند. سندنویسی جایگزین کد، تست یا اجرای واقعی MVP نیست.
